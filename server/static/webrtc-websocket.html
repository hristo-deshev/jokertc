WebRTC signaling test (/ws)

Open this page in two tabs. Put the same session id in both, pick initiator in one and answerer in the other, then Connect in both. The initiator creates the offer; the answerer replies to it. STUN and TURN come from the relay's ready message, so a connected call also proves the credential it issues works.

An initiator that connects and then sits alone follows the first remote_joined it sees: the announced session id goes into the box, the page rejoins on it, and the offer goes out when the relay reports both sides are present. So you can Connect on any id and let a device that picks its own session pull you to it. It only follows while it is still alone, and only once per Connect.

Initiator and answerer are sent on the wire as the roles phone and device, which is what the relay and the device firmware speak. The relay decides who offers, and always picks the phone.

For the copy/paste version with no signaling server, see /ui/manual.

Leave this on for the ESP device: it does not implement trickle ICE, so it needs every candidate inside the offer or answer. Turn it off only when both sides are browsers, where trickling connects sooner.

Sets iceTransportPolicy: 'relay', so this page gathers nothing but a TURN allocation, and drops every incoming candidate that is not typ relay, including the ones embedded in the remote SDP. Both ends then have to meet at the TURN server. Turning off STUN on the server does not do this: two peers on one LAN pair their host candidates and never ask a server anything. If the call fails with this on, the relay path is genuinely broken.

Leave this on for the ESP device. The browser default offers VP8, VP9, AV1, four H264 profiles and a retransmission codec for each, which the device cannot parse. This cuts the video section to one H264 payload type. It also stops the browser sending video, so in a two-tab test only the initiator sees a picture. Audio is receive-only in both modes and the microphone is never captured.
